# Analytically — Dentally Data Warehouse + embedded analytics

A multi-tenant analytics product for dental practices running on **Dentally**. It
ingests Dentally data, transforms it through a **Medallion** data warehouse on
**Microsoft Fabric**, and surfaces it as **Power BI reports embedded in a web app**
("Analytically"), with per-tenant row-level security.

## What's here

- **Data warehouse** (`Fabric/`) — T-SQL on a Fabric Warehouse (`WH_Dentally`), four medallion layers.
- **Web app** (`Web/`) — a Flask API + HTML/JS SPA that embeds the Power BI reports.
- **Reports / model** (`PBI/`, `Fabric/*.csx`) — the `.pbix` model + Deneb visual spec; KPI/measure logic as Tabular Editor C# scripts.
- **Release tooling** (`Scripts/`, `Releases/`, `Migrations/`) — manifest-driven warehouse deploys + tests.

## Architecture

**Medallion warehouse** — data flows through four schemas:

1. **Bronze** — raw Dentally API ingestion (minimal typing, all nullable).
2. **Silver** — cleaned + typed; MERGE/upsert incremental loads from Bronze; business logic (casts, lookups).
3. **Gold** — dimensional model (DROP/CREATE or upsert). `pk_*` surrogate, `bk_*` business, `fk_*` foreign keys; facts + dimensions + aggregates.
4. **PBI** — friendly-named presentation views (generated by `Meta.usp_Create_Gold_Views`) the semantic model imports.

Supporting schemas: **Audit** (ETL orchestration/logging + `Process_Config`/dependencies), **Meta** (view generation), **Config**/**Input** (reference + per-tenant config), **Security** (tenant access), **Test** (regression framework), **Migrate** (schema version + deploy log).

**SaaS embed** — the Flask app authenticates users (MSAL/Entra ID), looks them up in `Security.Application_Users`, and mints Power BI embed tokens **as a service principal** with the RLS **effective identity** set to the user — so each user sees only their client's tenant(s). Reports: Home, Revenue, Patient, Schedule, Clinical, NHS.

**Environments** — dev and prod are separate Fabric workspaces + warehouses; the web app runs on Azure Container Apps. See [RUNBOOK.md](RUNBOOK.md).

## Run the web app locally

Prereqs: Python 3.11, **ODBC Driver 18 for SQL Server**, an Entra app registration (service principal) with access to the Fabric workspace + warehouse.

```bash
cd Web
pip install -r requirements.txt
cp .env.example .env        # then fill in the values (see below)
gunicorn --bind 0.0.0.0:8000 app:app    # or: python app.py
```

Required env vars (`Web/.env`, gitignored — never commit it): `TENANT_ID`, `CLIENT_ID`,
`CLIENT_SECRET`, `WORKSPACE_ID`, `DATASET_ID`, `FABRIC_SERVER`, `FABRIC_DB`, and the
`REPORT_ID_*` per report. Optional: `ALLOWED_ORIGINS`, `REPORT_ROLES` (default `RLS`),
`FLASK_DEBUG`, `APP_ENV`. Health check: `GET /health` → `{"status":"ok"}`.

## Deploy

- **Web app** — CI/CD: push to `dev` → dev Container App; merge `dev`→`main` → prod (gated by `dw-tests`). Immutable `:<git-sha>` images.
- **Warehouse** — versioned manifests, run deliberately:
  ```powershell
  .\Scripts\Deploy.ps1 -Manifest Releases\Vnnn__<name>.manifest   # set $env:FABRIC_SERVER for prod
  ```
- **PBI model/reports** — promoted dev→prod via the Fabric deployment pipeline (with a parameter rule for the warehouse source).

Full procedures, rollback, and the incident playbook are in **[RUNBOOK.md](RUNBOOK.md)**.

## Conventions

Files: `[Schema].[Object].[Type].sql` (UTF-16 LE w/ BOM for SSMS-authored SQL).
Naming: `usp_Load_*`, `pk_/bk_/fk_`, `DW_*` metadata columns; acronyms fully capitalised (ID, NHS, UDA, UOA). See `CLAUDE.md`.
