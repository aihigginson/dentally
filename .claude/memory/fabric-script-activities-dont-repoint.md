**A Data Pipeline `Script` activity binds to a named connection, and that connection
does not repoint when the pipeline is promoted dev -> prod.** The promoted pipeline
runs happily against whatever the connection points at - in our case DEV. Nothing in
the run history looks wrong, because the run genuinely succeeds; it just succeeds on
the wrong database.

Found 2026-09-09: BOTH prod pipelines were affected for weeks.
- `Sync_Subscriptions` (hourly) -> prod `Security.Application_Users` kept 61 stale
  `no_access` rows and no subscription change ever reached prod's auth surface.
- `Generate_Invoices` -> prod `Billing.Invoice_Line` was EMPTY; the 17 lines sitting
  in dev had been generated by prod's own pipeline.
`Delta_Build_Nightly` was never affected because it uses a **Notebook** activity.

**The fix, and the rule: use a Notebook activity.** Item references (`notebookId`,
`workspaceId`) DO get remapped on promotion; connections do not. The notebook then
resolves its own warehouse so the dev and prod definitions stay identical:

```python
_ws_id = fabric.get_workspace_id()
_whs   = fabric.FabricRestClient().get("/v1/workspaces/" + _ws_id + "/warehouses").json()["value"]
endpoint = next(w for w in _whs if w["displayName"] == warehouse_name)["properties"]["connectionString"]
```

This is RUNBOOK golden rule 2 (written about the semantic-model source) applying to
pipelines as well.

**Two gotchas seen while fixing it.** `fetchone()` after a batch containing
`EXEC ... @OUT` raises - pyodbc is left on the proc's own result sets, so count around
the call instead. And a prod pipeline carrying a `.schedules` part that dev lacks shows
permanently as "Different from source" in the deployment pipeline: benign, and better
than the alternative, since it means promotion did NOT wipe the prod schedule.
