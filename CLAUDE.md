# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a T-SQL data warehouse for the **Dentally** dental practice management system. It ingests data from the Dentally API and transforms it through a **Medallion Architecture** into a Power BI-ready analytics layer. The target database is `dtly` (SQL Server 2022, compatibility level 170).

## Architecture: Medallion Layers

Data flows through four schemas in sequence:

1. **Bronze** — Raw API ingestion. Minimal typing (most columns `nvarchar`/`decimal`), all nullable. No business logic.
2. **Silver** — Cleaned and typed. MERGE-based incremental upserts from Bronze. Business logic applied here (type casting, lookups, case/when conversions).
3. **Gold** — Dimensional model. Load pattern differs by table type: **Dims** = MERGE upsert (keep `pk_*` across loads), **Facts** = hash-gated incremental MERGE upsert, **Aggs** = DROP/CREATE full rebuild. Surrogate keys (`pk_*`), business keys (`bk_*`), foreign keys (`fk_*`). Fact and Dimension tables.
4. **PBI** — Presentation views for Power BI. Friendly column names (spaces allowed). Generated by `Meta.usp_Create_Gold_Views`.

Supporting schemas:
- **Audit** — ETL orchestration and logging. Process execution log with UUID tracking, record count logs, environment configuration.
- **Meta** — Metadata-driven view generation.
- `dbo` — Utility functions.

## File Naming Convention

All 197 files follow: `[Schema].[ObjectName].[ObjectType].sql`

Object types in filenames: `Table`, `Stored Procedure`, `View`, `User Defined Function`, `Schema`, `Database`

## Object Naming Conventions

| Object | Pattern | Example |
|--------|---------|---------|
| Silver load procedures | `Silver.usp_Load_[Entity]` | `Silver.usp_Load_Patients` |
| Gold table DDL | `Gold.[Table].Table.sql` | `Gold.Dim_Patients.Table.sql` |
| Gold dimension load | `Gold.usp_Load_Dim_[Name]` | `Gold.usp_Load_Dim_Practitioners` |
| Audit procedures | `Audit.ETL_[Action]` | `Audit.ETL_Start_Run` |
| Functions | `fn_` prefix | `Gold.fn_Get_Date_Key` |
| Primary keys | `pk_[entity]` (integer identity) | `pk_patient` |
| Business keys | `bk_[entityname]` (source ID) | `bk_patient_id` |
| Foreign keys | `fk_[referenced_entity]` | `fk_practitioner` |
| DW metadata cols | `DW_` prefix | `DW_Loaded_At`, `DW_Created_At` |

Acronyms always fully capitalised: `ID`, `NHS`, `UDA`, `UOA`, `SMS`.

## Key Patterns

**Silver layer loads** use MERGE statements for incremental upserts keyed on business keys. Use `TRY_CAST` for safe type conversion from Bronze strings/decimals.

**Gold layer** load pattern is per table type — **Dims** MERGE-upsert and preserve their `pk_*` across loads (so downstream `fk_*` stay stable); **Facts** are incremental via a HASHBYTES-gated MERGE (unchanged source rows are skipped — a wrongly-loaded row can persist, so fk resolution depends on dims loading first); **Aggs** (tables reading other Gold facts) DROP/CREATE full-rebuild. Load order therefore matters: DIM → FACT → AGG. Date surrogate keys use days-since-1999 epoch via `Gold.fn_Get_Date_Key`.

**PBI views** use two naming sub-patterns:
- `PBI.List [Name]` — dimension/lookup views
- `PBI._[FactName]` — fact views (underscore prefix)

**Error handling** wraps logic with `Audit.ETL_Error_Handler` for consistent logging.

**Environment config** (workspace, lakehouse, warehouse mappings) is stored in `Audit.Environment_Config` table rather than external config files.

## Special Acronyms (for `dbo.CapitaliseSnakeCase`)

The function handles these as special cases: `ID`, `NHS`, `UDA`, `UOA`, `SMS`. Keep this list in mind when adding new column names that include abbreviations.

## File Encoding

All SQL files use **UTF-16 LE with BOM** — the default encoding when saving from SQL Server Management Studio. Maintain this encoding when creating new files.
